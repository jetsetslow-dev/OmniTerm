# OmniTerm Privacy

OmniTerm is designed as an on-device SSH/SFTP administration tool.

## Data The App Handles

OmniTerm stores the following data locally on the user's device when the user enters it:

- SSH host names, addresses, ports, usernames, groups, notes, and connection settings.
- SSH passwords, sudo passwords, proxy passwords, credential profiles, and imported private keys.
- Quick scripts, alert rules, Wake-on-LAN targets, app settings, and recent metric history.
- Fleet's run history: the last 50 Broadcast runs, including those automation, an AI assistant, a schedule or an alert's runbook started, which are saved from the moment they start, each with its command as written, which hosts it ran on, and the end of each host's output. The values typed for a script's `{{placeholders}}` are not kept, though a host's output can still show them. The history is included in app backups unless the user unticks Fleet history, and the user can delete a run or clear it all in Fleet.
- Automation tokens, if the user makes any under Tools → Automation: for each, the saved script and hosts it may run, the name the user gave it, when it was made and last used, whether its runs show a notification, and its last 300 uses: when, whether it succeeded, failed or was refused, and the names of the hosts it ran on or why it did not run. Only a SHA-256 fingerprint of each token is stored, never the token itself. Revoking a token deletes its uses. App backups include the tokens' fingerprints, what each may run, their notification choices and their uses, unless the user unticks Automation & AI assistants; the Automation switch is not included, and a restore leaves automation off.
- Fleet's schedules, if the user makes any under Fleet → Schedules: for each, its name, its saved script, its hosts (picked hosts, groups or tags), when it repeats, whether it is on, whether its runs show a notification, when it runs next, and how its last run went: when, whether it succeeded, failed or was refused, and a short line naming the hosts it failed on or why it did not run. App backups include the schedules unless the user unticks Automation & AI assistants; a restore leaves them paused.
- VPN tunnels the user adds under Tools → VPN tunnels: a name and the WireGuard configuration, including its private key, stored encrypted on the device; for a Tailscale tunnel instead, the control server's address, the auth key if the user gives one, and the device name, stored encrypted, and the keys and sign-in that make the phone a device in the tailnet, stored encrypted and read by that tunnel alone (they are never included in a backup and never leave the device); per host, which tunnel it goes through and its address inside the tunnel; and, per tunnel, the names of the Wi-Fi networks the user lists as ones it is not needed on.
- For a tunnel with such a list only: the name of the Wi-Fi the phone is on, kept on the device until the phone leaves that network, so that background checks know it too. It is never sent anywhere.
- AI assistant (MCP) settings, if the user turns that on under Tools → AI assistants: which hosts assistants may see, whether any command may be asked for, the ports, the host the server is reached through, whether its runs show a notification, and a SHA-256 fingerprint of its token, never the token itself. The last 200 calls are kept: when, the client's own name, the tool, whether it succeeded, failed or was refused, the first line of its answer, and, for a call that ran something, which run in Fleet's history it was. App backups include these settings and the token's fingerprint unless the user unticks Automation & AI assistants; the assistant's switch is not included, and a restore leaves it off. The calls are included unless the user unticks AI assistant log, and the user can clear them.
- Alert forwarding settings, if the user sets them up: the service, its address and topic, and an optional access token (stored encrypted).
- For a Backup Age alert rule: the repository, filter and settings-file path the user enters, and the repository password, stored encrypted. The check runs the backup tool on that host over the host's SSH connection, so the password goes only to that host, on the command's input; the phone itself connects to no backup server.
- SNMP devices the user adds under Tools → SNMP devices: a name, address and UDP port, the SNMP version, and the v2c community or the v3 user name, its authentication and privacy protocols and their passwords, stored encrypted; and, per device, the VPN tunnel it is reached through, if any. What a device answers (its name, location, uptime, CPU load, memory, disks, interfaces with their traffic, errors and discards, and a UPS's power, battery and load) is kept in memory only until the app closes. An alert rule on a device keeps its incidents and history like any other rule, with the reading that raised them, such as the names of the interfaces that went down or the UPS's charge.
- Proxmox VE servers the user adds under Tools → Proxmox VE: a name, address and port, the API token's ID and its secret, stored encrypted, the SHA-256 fingerprint of the server certificate the user trusted, notes, and the VPN tunnel it is reached through and its address there, if any. What the server answers (its version, nodes, guests with their state and resource use, snapshots and recent backup tasks, and which guests each scheduled backup job backed up, read from its log) is kept in memory only until the app closes.
- For image update checks (Containers → Images, or an Image Updates alert rule): the last check's result for each host, kept in memory only until the app closes. The host is asked over SSH to list the images its containers use and to send one `HEAD` request per image to that image's registry (for example Docker Hub or GitHub's registry), with an anonymous pull token where the registry asks for one, so the registry sees that host's address. The phone itself connects to no registry, nothing is pulled, and no registry sign-in is stored or sent.

## Network Use

The app connects directly from the user's device to servers and proxies configured by the user, or, for a host the user set a VPN tunnel for, through that tunnel to the peer its configuration names. A tunnel runs inside the app only, does not use Android's VPN service, and carries only OmniTerm's connections to the hosts that use it; a host with a tunnel is never connected to directly, except while the phone is on a Wi-Fi the user listed on that tunnel as one it is not needed on. OmniTerm does not operate a backend service for telemetry, analytics, advertising, crash reporting, or credential sync.

SNMP devices are read from the phone itself, over UDP to the address and port the user entered: while Tools → SNMP devices is open, when the user taps Poll, and about once a minute for a device an alert rule that is switched on watches, while alerts are on and the app is polling hosts. Only read requests (GET and GETBULK) are sent; nothing on a device is changed. A v2c community is sent as SNMPv2c sends it, unencrypted, so anyone on the network path can read it; SNMPv3 with authentication and privacy signs and encrypts each request. VPN tunnels carry only TCP, so a device the user set a tunnel for is not polled at all while that tunnel is in use, and never directly instead.

Proxmox VE servers are read from the phone itself, over HTTPS to the address and port the user entered, when Tools → Proxmox VE is open, when the user taps Refresh, when the user acts on a guest, and every 15 minutes for a Backup Age rule on vzdump backups with no dump folder, on a host with the same address as the server, while that host is checked. That check only reads the server's backup tasks. The API token goes only to that server, in the request's Authorization header, never in an address, and only after its certificate is one the phone's certificate authorities trust or the one whose fingerprint the user trusted; otherwise the connection stops before anything is sent. Redirects are not followed. A server the user set a tunnel for is reached only through it, as hosts are. Starting, stopping and rebooting guests and taking, rolling back or deleting snapshots happen only when the user taps them on that screen; schedules, alert runbooks, automation and AI assistants cannot do them.

### Tailscale tunnels

A Tailscale tunnel joins the phone to the user's tailnet as a device of its own, inside the app. While it runs, it talks to the control server the user chose: Tailscale's coordination server when the address is left empty, which is operated by Tailscale Inc. under its own privacy policy, or the user's own Headscale server. The control server learns what any Tailscale device tells it: the device's public keys, the name the user gave it, its addresses in the tailnet, the public address and port it connects from and the addresses of the phone's own network interfaces (so other devices can reach it directly), the operating system and its version, the version of the Tailscale library, and network conditions such as whether IPv6 and UDP work and how far each relay is. To find its public address and relay distances, the tunnel exchanges small requests with the relays (DERP servers) the control server lists, and it carries traffic through them when a direct path is not possible; that traffic is end-to-end encrypted with WireGuard. OmniTerm's build of the library uploads no logs, metrics or device posture, and does not report the phone's open ports. Only OmniTerm's connections to hosts that use the tunnel go through it; the tunnel never uses an exit node and is never the phone's VPN.

## Alert Forwarding (Opt-In)

Alert forwarding is off unless the user sets it up under Alerts. When it is on, each alert that opens (and, if the user keeps that option, each one that resolves) is sent from the device to the one address the user entered: an ntfy server and topic, a Gotify server, or a webhook. The message carries the alert's title and text (the host's or device's name, the rule, the reading and its threshold), its severity and the time. For a Script Check rule, the text also includes the script's name and the first line it printed, since that line is the reason the check gives. Nothing else is sent: no credentials, files, terminal output or other metrics. Muted alerts are not forwarded. An access token the user enters is stored encrypted on the device with the Android Keystore and sent only to that address; redirects are not followed, so it never goes anywhere else. A plain `http://` address sends the alert and token unencrypted, and the form says so. On a public ntfy server, anyone who knows the topic can read its messages. The service receiving the alerts is the user's choice and is governed by its own terms.

## Automation (Opt-In)

Automation is off unless the user turns it on under Tools → Automation. When it is on, another app on the device that presents a token the user made (Tasker, for example) can run that token's saved script on its hosts. The run happens as any Fleet run does, directly from the device to those hosts. Its result (each host's output, its exit status and which hosts failed) goes back only to the app that asked: to Tasker on its completion intent, which must name an app, or as a broadcast to the one package the request named. A request with a token OmniTerm does not know is ignored and gets no answer. The token is shown once, when it is made; the app the user gives it to keeps it (Tasker stores it in its action, so its exports and backups contain it). Revoking a token in OmniTerm stops it working.

## AI Assistants Over MCP (Opt-In)

The MCP server is off unless the user turns it on under Tools → AI assistants, which needs App Lock, the screen lock, or a plain confirmation on a phone without one, and makes a token that is shown once. While it is on, an ongoing notification says so and can turn it off.

It listens only on the phone's own loopback address (127.0.0.1), so no other device on the network can reach it. Apps on the phone can reach that address, so every request must carry the token; requests that name another host or come from a web page are refused. If the user picks one of their saved hosts to reach the server from a computer, OmniTerm keeps a reverse SSH tunnel open to that host, which listens only on the host's own loopback address. Traffic then goes between the phone and the user's own host over SSH, and stays on the user's machines.

An assistant can see only the hosts the user ticked, none by default. For those it can read the host's name, group, online state, health score and latency; the metrics and alerts OmniTerm last recorded; the host's containers, which OmniTerm signs in to read; and the names, categories and `{{values}}` of saved scripts, but not their commands. It is never given a host's address, user name, passwords, keys, notes or any file. Running a saved script, or a typed command if the user allows that, waits for the user to approve that one run on the phone, where the full command is shown, and approving needs the same lock check. A run that is refused or not answered within two minutes does not happen. Runs are kept in Fleet's history like any other run.

Whatever an assistant reads, including the output of runs the user approves, goes to that assistant program, and from there it may reach the company behind it, under that company's terms. OmniTerm says so on the screen before it is turned on. Revoking the token, or turning the server off, stops every assistant at once.

## Links And Shares From Other Apps

Another app can open an `ssh://` link in OmniTerm or share text or files with it. That only opens a screen: nothing connects, is saved or is uploaded until the user taps. From a link, OmniTerm reads the address, port and user; a password or other parameters in the link are dropped and never stored. Shared text fills in a new script, which is saved only if the user saves it. Shared files are read only when the user taps Upload here, and only to send them to the host and folder the user opened; OmniTerm keeps no copy. It reads only what another app shares through Android's content sharing, never a raw file path or OmniTerm's own files. This needs no extra permission.

## Advertising (Play Store Build Only)

The free Play Store build shows a single banner ad served by Google AdMob. AdMob may collect device identifiers and ad-interaction data as described in [Google's privacy policy](https://policies.google.com/privacy). In the EEA/UK, ads are only requested after consent is collected through Google's User Messaging Platform. Purchasing ad removal or the full unlock removes the banner and stops all ad requests. The source-available build contains no ad SDK and makes no ad requests.

## Sharing And Sale

OmniTerm does not sell user data. It does not share credentials, private keys, host inventory, metrics, or files with the project maintainers or third-party services. The exceptions are the ones the user turns on: alert forwarding sends alerts to the service the user chose, automation sends a run's result to the app on the device that asked for it with the user's token, and the MCP server answers the AI assistant that presents its token, as described above.

User-initiated SSH/SFTP operations send data directly to the host or proxy selected by the user. User-initiated exports, CSV files, and encrypted backups are written only to destinations selected through Android's system document picker.

## Backups

Android platform auto-backup is disabled because local app data can include SSH credentials and private keys.

VPN tunnels, private keys and Tailscale auth keys included, SNMP devices, with their communities and passwords, and Proxmox VE servers, with their API tokens and trusted certificate fingerprints, are part of a backup that includes hosts; such a backup is always encrypted. Alert rules carry a Backup Age rule's repository password, and such a rule is restored switched off, as are an Image Updates rule and a rule on an SNMP device. A Tailscale tunnel's device keys are not: a restored Tailscale tunnel signs in again as a new device.

A backup's settings include App Lock's PIN, as the salted hash the app stores, and whether the lock is on. Biometric unlock and failed PIN attempts are never included. Restoring a backup made with App Lock off never turns the restoring phone's lock off.

The in-app backup feature is user initiated. It encrypts exported app data with AES-256-GCM using a passphrase-derived key. The passphrase is not stored by OmniTerm and is required to restore the backup.

## Permissions

OmniTerm requests only permissions needed for its visible features:

- `INTERNET` for SSH and SFTP connections to user-configured hosts.
- `ACCESS_LOCAL_NETWORK` (Android 17 and later) to reach hosts, shares and devices on your local network: SSH, SFTP, LAN discovery, tunnels, shares and Wake-on-LAN.
- `USE_BIOMETRIC` for optional app lock and privileged-action confirmation.
- `POST_NOTIFICATIONS`, `FOREGROUND_SERVICE`, `FOREGROUND_SERVICE_CONNECTED_DEVICE`, and `CHANGE_NETWORK_STATE` for the optional background SSH keep-alive notification, monitoring alerts, and, while the user has it on, the MCP server's notification and its requests for approval. The notification of a run automation, an AI assistant, a schedule or an alert's runbook started, shown as the user chooses for each token, schedule and rule, names who started it, the script, how many hosts are done and, when the run fails, the hosts it failed on; like any notification, it can show on the lock screen as the phone's settings allow.
- `ACCESS_NETWORK_STATE` to tell whether the phone has a network at all, so the Host Offline alert and the checks the phone runs itself record nothing while it is offline instead of reporting every host as down; and whether that network is Wi-Fi, for a VPN tunnel the user says is not needed on some Wi-Fi.
- `ACCESS_FINE_LOCATION`, `ACCESS_COARSE_LOCATION` and `ACCESS_WIFI_STATE`, only for a VPN tunnel the user says is not needed on some Wi-Fi. Android gives an app the name of the Wi-Fi the phone is on only with precise location allowed, so OmniTerm asks for it when the user lists a Wi-Fi on a tunnel, and never otherwise. It reads the Wi-Fi's name and nothing else: no position is requested, read or stored, and the name does not leave the device. Location in the background ("Allow all the time") is not requested; while the app is closed it uses the name it last read for the same Wi-Fi connection, and the tunnel when it has none. Without the permission the tunnel is always used.
- `FOREGROUND_SERVICE_DATA_SYNC` for the progress notification that keeps a long file copy or other long operation running while the app is in the background.
- `WAKE_LOCK` to keep an explicitly backgrounded live terminal from being suspended mid-session.
- `RECEIVE_BOOT_COMPLETED` so that Android keeps the job each of Fleet's schedules waits as when the phone restarts. OmniTerm starts nothing when the phone starts; Android runs a schedule when it is due, only while the schedule is on.
- `NFC` to talk to a FIDO2 security key you hold to the phone when you sign in with it or make a key on it. USB security keys and USB serial consoles use Android's per-device USB permission prompt instead.

The app does not request Android storage permissions or All Files Access. File import and export use Android's Storage Access Framework.

## Data Deletion

Users can delete hosts, credentials, keys, scripts, alerts, and Wake-on-LAN targets inside the app. Uninstalling the app removes its local database and settings from the device.
